# ADR-0005: PostgreSQL over MongoDB

- **Status:** Accepted
- **Date:** 2026-10-01

## Context

- `CLAUDE.md` set PostgreSQL as a development standard from the start of the project, but no ADR ever recorded why — it was an assumed default, not a weighed decision.
- The core domain is a ledger: customers, accounts, and an append-only transaction log, with strict requirements already in force — NFR-1 (concurrency correctness), NFR-3 (exact decimal arithmetic), and NFR-7 (deterministic schema migrations).
- Two broad options exist for the primary datastore: a relational database (PostgreSQL) or a document store (MongoDB).

## Decision

Use PostgreSQL as the system of record for all domain data, both in the current monolith and in each extracted microservice's own database going forward (per [ADR-0004](./ADR-0004.md)).

## Consequences

**Positive**
- The domain is naturally relational — `customers → accounts → ledger_entries`, enforced by foreign keys — which a document model would have to work around rather than express directly.
- NFR-1's locking strategy (`AccountRepository.lockById` plus an insert, in one transaction) is a native, well-supported pattern in Postgres. Multi-document transactional guarantees in MongoDB exist but are the exception to its usual mode of operation, not the default.
- NFR-3 (exact monetary values) is served directly by `NUMERIC(19,2)`, a first-class fixed-point type. MongoDB's `Decimal128` exists but is less central to its tooling and ecosystem.
- NFR-7 (deterministic, versioned schema changes) maps directly onto Flyway migrations against a real schema. A schemaless store trades this property away by design.
- Matches how core banking systems are built in practice — relational or purpose-built ledger stores, for the same ACID and integrity reasons.

**Negative**
- Horizontal write scaling is harder than with a document store built for it. Not a current bottleneck, and standard relational scaling paths (read replicas, partitioning, eventually sharding the ledger by account range) are available if it becomes one.
- Schema changes require a migration rather than being implicit. This is treated as a feature, not a cost — see NFR-7.

## Alternatives Considered

- **MongoDB.** Rejected: its real strengths — flexible schema, horizontal write throughput — aren't problems this project has, while its weaker default consistency model works against NFR-1 and NFR-3, which are not optional for a ledger.
