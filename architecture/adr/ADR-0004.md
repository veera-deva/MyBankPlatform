# ADR-0004: Adopt Microservices Architecture

- **Status:** Accepted. Supersedes [ADR-0001](./ADR-0001.md).
- **Date:** 2026-09-30

## Context

- [ADR-0001](./ADR-0001.md) deliberately deferred distributed-systems concerns until the core banking domain — the ledger, concurrency safety, authentication — was correct and proven by tests. As of 2026-09-30, M0 is complete: FR-1 through FR-7 are implemented, NFR-1 (concurrency correctness) is enforced, and the ledger API is covered end-to-end by automated tests (T1–T6).
- The primary goal of this project is hands-on capability with complete distributed systems, and the roadmap explicitly calls for gRPC, Kafka, per-service databases, and eventual AWS deployment via IaC.
- Continuing to add features to the monolith would keep delaying the concerns (network partial failure, eventual consistency, service-to-service auth, the transactional outbox pattern) that are the actual learning objective from this point forward.

## Decision

Move from the modular monolith to a microservices architecture, split along the domain boundaries below, with a database per service. This is a staged migration (M1–M9 in the roadmap), not a rewrite — existing, tested monolith code is extracted service by service, starting with the safest extraction first.

| Service | Owns | Notes |
|---|---|---|
| `api-gateway` | Routing, edge auth | Backend services must not be directly reachable from outside the gateway |
| `identity-service` | Customers, login, JWT issuance | Extracted from the current `AuthService` |
| `core-banking-service` | Accounts and the ledger | Kept together deliberately — NFR-1 depends on one database transaction holding the row lock and writing the ledger entry in the same unit of work. Splitting these would destroy that guarantee and require a saga, which is out of scope until it's understood in its simple, single-database form first (see ADR-0001). |
| `notification-service` | Consumes ledger events | The first and safest extraction — a pure consumer, with no state of its own to protect |
| `transfer-service` (later) | Money movement between accounts | Deliberately deferred — this is where sagas and real distributed-transaction problems first appear, once the simpler extractions are understood |

**Supporting technical decisions bundled into this ADR:**

- **Inter-service synchronous calls: gRPC.** Used where one service needs a direct answer from another — e.g. `core-banking-service` asking `identity-service` "does this customer exist and is it active?" when opening an account, a check that today is a JPA foreign key and becomes a real design question once the databases are separate.
- **Inter-service events: Kafka**, keyed by `accountId` so events for one account stay ordered. `core-banking-service` publishes `TransactionPosted`; `notification-service` consumes it.
- **Delivery guarantee: build the naive dual-write first, then fix it with the Transactional Outbox pattern.** Writing to the database and to Kafka as two separate, unguaranteed operations means "money moved but nobody was told," or the reverse. The naive version is built and observed failing before being corrected — a deliberate lesson, not an oversight (see M3/M4 in the roadmap).
- **IaC tool: Terraform**, over AWS CDK — chosen for reviewable `plan` output, and because CDK's higher-level constructs (e.g. `ApplicationLoadBalancedFargateService`) silently create roughly 20 resources, which works against the goal of understanding what each piece (VPC, subnets, ALB, IAM roles) actually does.
- **Compute target: ECS Fargate first**, with EKS/Kubernetes as a later capstone (M10) — fewer moving parts while distributed-systems fundamentals are still being learned. Kubernetes itself is rehearsed locally with `kind` in the meantime.

## Consequences

**Positive**
- Directly serves the project's actual goal: hands-on experience with service boundaries, gRPC, Kafka, per-service databases, and IaC deployment to real AWS.
- The domain boundaries were chosen to protect NFR-1 rather than copy a generic reference split — `core-banking-service` keeps accounts and the ledger together specifically because that transaction boundary cannot be safely split without first learning sagas.

**Negative**
- NFR-1's current single-transaction guarantee no longer extends past `core-banking-service`'s boundary. Any future operation spanning services (a transfer between two accounts, or an operation depending on `identity-service` being reachable) needs an explicit consistency strategy (saga, outbox) — it's no longer given for free by the database.
- Operational complexity increases substantially: multiple deploy units, inter-service network calls that can partially fail, and — once on real AWS — hourly cost for NAT gateways, ALBs, RDS, and MSK, even while idle.
- The account-ownership check (`AccountTransactionService.ownedAccount`, which protects NFR-4) will need to be redesigned once `identity-service` and `core-banking-service` have separate databases — `Account` can no longer hold a JPA relationship to `Customer` across a database boundary. This is intentionally left as an open design question for M1, not resolved by this ADR.

## Alternatives Considered

- **Stay on the modular monolith and simulate distributed-systems concepts internally** (e.g. an in-process event bus instead of Kafka). Rejected: the project's explicit goal is operational experience with the real technologies, which an in-process simulation cannot substitute for.
- **Split directly into the reference architecture's own service boundaries** (a patient/billing/analytics-shaped split). Rejected: those boundaries don't correspond to this domain, and the reference implementation carries known anti-patterns (see ADR-0001) that should not be inherited by copying its structure.
