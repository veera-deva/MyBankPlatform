# ADR-0002: Ledger as Source of Truth

- **Status:** Accepted
- **Date:** 2026-09-01

> **Note on provenance:** this ADR was referenced by `frd.md`/`nfr.md` from early in the project but never actually written to a file. Reconstructed 2026-09-30 from the decision as it was actually built and tested.

## Context

- The account balance is the single most important, most frequently read, and most easily corrupted piece of state in a banking system.
- Two general designs were available: (a) a mutable `balance` column on the account row, updated in place on every deposit/withdrawal, or (b) an append-only, insert-only log of every transaction, with the current balance derived from that log.
- A mutable-balance design is prone to silent corruption: any code path that writes the balance column without the exact same locking discipline can desync it from reality — and once overwritten, the history of how it got there is gone.

## Decision

The `accounts` table never stores a balance column. Every deposit and withdrawal appends an immutable row to `ledger_entries`, recording the transaction type, amount, and the resulting `balance_after` at that point in time. The current balance is always derived — `LedgerService.currentBalance` reads it via `findTopByAccountIdOrderByCreatedAtDesc(accountId)?.balanceAfter`.

## Consequences

**Positive**
- NFR-2 (auditability) is structurally guaranteed rather than only a policy: there is no balance column to accidentally overwrite, and the full history of how any balance was reached is always reconstructable.
- Concurrency bugs become visible instead of silent: if the row lock backing NFR-1 were ever dropped from `deposit`/`withdraw`, the derived balance would visibly diverge from a correct implementation, rather than quietly drifting.

**Negative**
- Reading the current balance requires a query (`ORDER BY created_at DESC LIMIT 1`) rather than a single-column read. Acceptable at this scale; a covering index or a periodic materialized balance would be the next step at higher volume — not needed yet.

## Alternatives Considered

- **A mutable `balance` column updated in the same transaction as each ledger insert** (a "belt and suspenders" approach some real systems use for read performance). Rejected for v1: the entire point of this design is to internalize ledger-as-source-of-truth thinking before optimizing around it.
