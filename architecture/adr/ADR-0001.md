# ADR-0001: Modular Monolith over Microservices for v1

- **Status:** Superseded by [ADR-0004](./ADR-0004.md) (2026-09-30)
- **Date:** 2026-07-06

> **Note on provenance:** this ADR was referenced by `nfr.md` from the start of the project but never actually written to a file. Reconstructed 2026-09-30 from the decision as it was actually made and built.

## Context

- The long-term goal of this project (per `CLAUDE.md`) is to become capable of designing complete distributed systems — the roadmap explicitly includes microservices, gRPC, Kafka, and Kubernetes.
- At project start, no working code existed yet. The core banking domain — accounts, the ledger, concurrency-safe balances, authentication — was not yet built or proven correct.
- A reference microservices-banking repository was examined during planning. It demonstrated the common failure modes of splitting too early: dual writes to the database and Kafka with no outbox, a hard-coded JWT secret in Java source, `host.docker.internal` service discovery, a single-broker Kafka cluster, no TLS. The distributed-systems seams were exactly where that demo cut corners.
- Building the core domain and a distributed system at the same time means debugging two hard problems at once, with no way to tell which one is at fault when something breaks.

## Decision

Build v1 as a single deployable Spring Boot application — one codebase, one Postgres database, one deploy unit. Internal package structure (`domain/`, `service/`, `repository/`, `web/`, `security/`) enforces logical separation of concerns, but all communication between them is in-process method calls, not network calls. No service boundaries, no inter-service messaging, no database-per-service in v1.

## Consequences

**Positive**
- NFR-1 (correctness under concurrency) is straightforward to guarantee: one database, one transaction, a single pessimistic row lock covers the ledger write and the balance read together. In a split system this becomes a distributed-transaction / saga problem, deliberately deferred rather than solved prematurely.
- Faster iteration: no network calls, no service discovery, no partial-failure handling to build before the core domain even works.
- Simpler debugging while learning: a single JVM process, a single stack trace, no need to correlate logs across services yet.

**Negative**
- Does not exercise the distributed-systems concerns (network partial failure, eventual consistency, service-to-service auth) that are a primary goal of this project. Accepted deliberately — deferred, not abandoned.
- The whole application is one deploy unit; any change requires redeploying everything. Acceptable for v1 with no real users.

## Alternatives Considered

- **Microservices from day one**, split along the reference project's own boundaries. Rejected: makes NFR-1 materially harder before the ledger logic itself was proven correct, and risks copying the reference implementation's known anti-patterns under time pressure.
- **A "modulith" with enforced module boundaries** (e.g. Spring Modulith / ArchUnit), still one deploy unit. Considered as a middle ground; deferred, but worth revisiting if boundary discipline becomes an issue before the physical split in ADR-0004.
