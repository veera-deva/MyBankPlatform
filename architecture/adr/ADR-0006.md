# ADR-0006: REST over GraphQL for the External API

- **Status:** Accepted
- **Date:** 2026-10-01

## Context

- `CLAUDE.md` set REST APIs as a development standard from the start of the project, but no ADR ever recorded why — it was an assumed default, not a weighed decision.
- The ledger API (T4/T5) already leans on HTTP status codes to carry real meaning: 404 for an account that's missing or not yours (NFR-4), 422 for insufficient funds, 401 vs 403 for authentication vs authorization.
- [ADR-0004](./ADR-0004.md) already chose gRPC for internal, synchronous service-to-service calls (e.g. `core-banking-service` asking `identity-service` if a customer exists).
- The eventual Android client (per `CLAUDE.md`'s project context) could benefit from GraphQL-style client-driven field selection, but that client doesn't exist yet.

## Decision

Use REST (with OpenAPI, already a listed standard) for the externally-facing API that clients call — the gateway and each service's public endpoints. GraphQL is not adopted.

## Consequences

**Positive**
- Preserves the status-code vocabulary already built and tested: 404/403/422/401 each carry distinct, deliberate meaning (see T4/T5 and [ADR-0004](./ADR-0004.md)'s NFR-4 discussion). GraphQL typically flattens responses to `200 OK` plus an `errors` array, which would have erased that distinction.
- Keeps the system to two paradigms, not three: REST for external calls, gRPC for internal calls. Adding GraphQL would introduce a third contract style without a problem it uniquely solves right now.
- Matches real-world practice for banking APIs — Open Banking / PSD2-style standards are REST-based, which keeps this project's experience transferable to real jobs.

**Negative**
- Clients that want exactly one shaped response across multiple resources (e.g. account + balance + recent transactions in one call) must either make multiple REST calls or wait for a purpose-built aggregating endpoint. Acceptable for now; revisit if the Android client's needs make this a real cost.

## Alternatives Considered

- **GraphQL for the external API.** Rejected for now: its main benefit — flexible, client-driven queries — isn't a current pain point, while its costs (a single endpoint, per-field authorization, N+1 query risk, different caching model) are real and immediate. Not ruled out permanently; could be revisited specifically for the Android client once it exists, as an addition alongside REST rather than a replacement.
